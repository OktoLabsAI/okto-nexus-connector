# M4m: bounded pre-ready repair and resumable release backfill

The previous reconnect path retired up to 4,096 resolved release checkpoints before the control link could become Ready. A larger accepted history raised `RECONCILIATION_REQUIRED` indefinitely, even though each checkpoint had durable Server proof. The repair now processes one indexed page (at most 128 rows) before reconciliation. Once the Server accepts the reconciliation, the existing independent checkpoint worker continues the remaining history. It marks each completed release in the outbox, so a worker interruption or later reconnect resumes from the pending index. A corrupt or failed checkpoint in the first pre-ready page still fails closed.

Verification used the final installed Connector 0.0.10 wheel with Core 0.0.12. All 29 event-recovery and release-reconciliation tests passed from site-packages. One test seeded 4,097 accepted releases in a single transaction and confirmed the reconnect path returned after 128 checkpoints, leaving 3,969 for background work instead of rejecting Ready. A separate 129-release test confirmed that an accepted reconciliation drains the remaining page. The previous tests continue to cover interrupted and idempotent checkpoint repair.

The physical directory audit remains an admission prerequisite. This change does not relax that fence. The major remote-Pi UI/restart gate was performed at M4l; this backfill change is limited to old accepted history and was verified with installed tests.

The indexed pending lookup was also measured with the installed wheel against a query-only fixture containing 1k, 10k and 100k retired historical rows plus the same three valid pending releases. The query returned three rows at every size. SQLite VM instructions were bounded by 99, 199 and 99 respectively (progress-handler interval: 100); the plan was `SEARCH releases USING INDEX release_event_retirement` on server, executor and rowid. Observed query times were 0.838, 2.655 and 0.541 ms; these are local cache measurements, not end-to-end startup times. Historical rows in this probe were already retired and were never decoded, so this specifically qualifies pending-index lookup cost. The 4,097-row installed test above qualifies the reconnect/backfill behavior.
